How we test

The same checks for every app, in eight steps

Each comparison follows these steps, in this order. Each comparison page also lists its own checks, so anyone can repeat them.

If you make one of the apps: your right of reply

  • We tell you before we test, and what we will check.
  • You see your own results before anyone else.
  • You have three working days to correct a fact or object.
  • A correction we can confirm changes the result. Your objection is shown next to it.

None of this costs anything. What every maker gets

The steps

From request to published result

  1. Pick a request with look-alike apps

    We start from a popular feature request on Atlassian's public request tracker that several store apps claim to answer. We note its votes and watchers on the day we read them.

    • Makers

    Tell the makers first

    Before we test, we tell each maker what we will check and how. We also read each app's terms.

    • Makers

    Ask first where the terms are unclear

    Where an app's terms do not clearly allow publishing test results, we ask its maker first and publish only after a yes. Until then, and if the answer is no, we list the app as not tested and say why. After a yes, the result is published whatever it shows.

  4. Install each app on our own test site

    We install each app on a test site that belongs to the lab, in Confluence or Jira, on the plan named on the comparison page. We never test on a customer's site or a maker's own systems.

  5. Run the same checks

    Every app gets the same pages and the same checks, run by the same scripts. We save what we read from the site as evidence, such as the page order after each check.

    • Makers
    • Right of reply

    Show each maker their results before publishing

    Each maker sees their own results first and has three working days to correct a fact or object. A correction we can confirm changes the result; an objection is shown next to it.

  7. Publish

    We publish what each app does and does not do, with the evidence, the version we tested and the date. Reading is free.

  8. Correct openly

    If we got something wrong, we fix it within three working days and add a dated note to the page. We never change a result without saying so.

How to read a result

  • Passed

    The app did what the check asks.

  • Partly

    The app did some of it. The note says which part.

  • Failed

    The app did not do it.

  • Could not run

    The check could not run on this app, for example because it has no such setting. It is left out of the count.

  • Not tested

    The app is listed, with the reason we could not test it.

A count such as 4 of 5 checks means four checks passed out of the five that could run.

The rules

What we always do, and never do

  • Every app gets the same pages, the same checks and the same scripts.
  • We test only on the lab's own Confluence and Jira site.
  • An app is included because it claims to answer the request, whether its maker pays or not.
  • Money never changes a result, a rank or a sentence.
  • A paid re-test is published like any other, whatever it shows.
  • We never change a result without a dated note on the page.

What we do not measure

We report what each app does, not how fast it does it. Speed on our test site says little about speed on yours, so we publish no speed figures.

Who pays for this

Makers can pay for deeper private reports and re-tests, never for results. Reading is free for everyone.
